# RoomLoom

RoomLoom rebuilds a place, remembered, planned or imagined, from a sketch, old photos and conversation with an AI agent, as a walkable 3D model in the browser.
Use `RoomLoom` as the display name and `roomloom` for packages, folders and identifiers.

## Current state

The repo scaffold (task T01), the scene schema (task T02), the project store with history and photo uploads (task T03), the Miro importer (task T04) and the 3D shell geometry (task T05) exist so far. The backend serves projects over a REST API (see [Projects, history and assets](#projects-history-and-assets)); the browser does not use it yet. New projects are created by importing a Miro sketch from the command line (see [Import a building from Miro](#import-a-building-from-miro)). Running the app shows a test page: a rotating box and a badge that says whether the frontend can reach the backend. A developer page shows a project's building in 3D (see [View the building shell](#view-the-building-shell)). Walking, the minimap and the agent come in later tasks.

The scene document format is defined by the Pydantic models in `backend/app/schema/`. A hand-made example project, `projects/example-l-house/`, holds an L-shaped building with five rooms, a sunken gym reached by two steps, a flat roof, three objects and one photo pin. Tests use it as their fixture.

## Prerequisites

| Tool | Version | Install (macOS) |
|---|---|---|
| [uv](https://docs.astral.sh/uv/) | recent | `brew install uv` |
| Python | 3.12 (uv manages it) | `uv python install 3.12` |
| Node.js | 22.12+ (or 24 / 26) | `brew install node` |
| GNU Make | any | ships with the Xcode command line tools |

No API keys are needed to run the app. Importing from Miro needs `MIRO_TOKEN` (and optionally `MIRO_BOARD_ID`) in `.env`; `--llm-notes` also needs `ANTHROPIC_API_KEY`.

## Run the app

1. **Clone the repo and enter it.**
   ```sh
   git clone <repo-url> roomloom
   cd roomloom
   ```
2. **Create your local env file.** Leave the keys empty for now.
   ```sh
   cp .env.example .env
   ```
3. **Start everything.**
   ```sh
   make dev
   ```
   This installs the Python and npm dependencies on the first run (about a minute), and again only when a lockfile changes. Then it starts:
   - the backend (FastAPI) on http://localhost:8000
   - the frontend (Vite) on http://localhost:5173, which forwards `/api` requests to the backend
4. **Open http://localhost:5173 in your browser.** You should see:
   - a dark grey page filling the window
   - a sand-coloured cube slowly rotating in the centre
   - a small badge in the top-right corner reading **`backend: ok`** in green
5. **Stop everything** with `Ctrl-C` in the terminal running `make dev`. Both servers stop. If one server exits on its own (a crash, or a port already in use), `make dev` stops the other one as well. The final `make: *** [dev] Error` line is expected and harmless.

### Optional checks

- **The backend answers directly:** `curl localhost:8000/api/health` prints `{"status":"ok"}`.
- **The proxy works:** `curl localhost:5173/api/health` prints the same thing.
- **The badge reacts to the backend:** stop only the backend, and within 5 seconds the badge turns red and reads `backend: down`. It turns green again once the backend is back. To try this, run the two servers in separate terminals:
  ```sh
  # terminal 1
  cd backend && uv run uvicorn --factory app.main:create_app --reload --port 8000
  # terminal 2
  cd frontend && npm run dev
  ```
- **Interactive API docs** (generated by FastAPI) are at http://localhost:8000/docs.

## Test and lint

```sh
make test   # pytest (backend) and vitest (frontend)
make lint   # ruff, tsc, eslint and prettier --check
```

Both should finish without errors. When Claude Code edits files, a hook (`.claude/hooks/lint-edited.sh`) formats and lints each edited file automatically.

## Regenerate the shared types

The Pydantic models in `backend/app/schema/` are the single source of truth for the scene format. After changing them, run:

```sh
make types
```

This rewrites three generated files (never edit them by hand):
- `shared/scene.schema.json`: the JSON Schema of a scene
- `shared/ops.schema.json`: a placeholder until the ops engine exists
- `frontend/src/types/scene.ts`: TypeScript types, generated from the schema with `json-schema-to-typescript`

Running it twice gives no diff. `make test` fails if the shared schemas are out of date.

## Projects, history and assets

Each project is a folder `projects/<slug>/` (set `PROJECTS_DIR` in `.env` to keep them elsewhere):

```
project.json            name, description, language, ...
scene.json              the current scene, always written atomically
history/index.jsonl     one line per change set: seq, time, source, description, label, scene_version
history/<seq>.json.gz   the full scene right after that change set
assets/<sha256>.<ext>   uploaded photos and textures, stored once per content, never deleted
assets/thumbs/          320 px JPEG thumbnails
thumbnail.jpg           the project-picker image
```

Every change is saved as a full snapshot. Restoring an old change set never deletes anything: it adds a new change set ("Restored to #3"). A project with a scene but no history (like the example project) gets a first "Imported" entry on its first change. While the app runs, the example project gains `history/`, `assets/thumbs/` and `thumbnail.jpg`; git ignores them. Changes to its `scene.json` do show up in `git status`; undo them with `git checkout projects/example-l-house`.

Uploaded photos are turned upright using their EXIF orientation, stripped of all EXIF data (including GPS position), shrunk to at most 4096 px on the long side and saved as JPEG.

Try it with the backend running (`make dev`):

```sh
curl localhost:8000/api/projects                                     # project cards
curl localhost:8000/api/projects/example-l-house/scene               # current scene
curl -F file=@photo.jpg localhost:8000/api/projects/example-l-house/assets   # upload a photo
curl localhost:8000/api/projects/example-l-house/history             # change sets
curl -X POST localhost:8000/api/projects/example-l-house/history/1/restore
curl -X POST -H 'content-type: application/json' -d '{"label": "Before furniture"}' \
  localhost:8000/api/projects/example-l-house/history/1/label
```

Other endpoints: `GET /api/projects/{slug}`, `GET /api/projects/{slug}/assets/{id}` (add `?thumb=1` for the thumbnail), and `POST` / `GET /api/projects/{slug}/thumbnail`. All of them are listed at http://localhost:8000/docs.

## Import a building from Miro

The building shell (rooms, walls, doors, windows, floor levels) is created once, from a Miro board drawn by a few rules (the full drawing guide is `plan/miro-conventions.md` in the local planning folder): one frame titled `Plan`, one thin rectangle labelled with its real length as the scale bar (e.g. `5 m`; a line drawn with Miro's line tool only works if both its ends are attached to shapes, because Miro's API gives no position for free line ends), named room rectangles (`Room 3A #classroom h=3.2`), red doors, light-blue windows, grey passages, orange stickies for `level -0.3` / `steps 2`, yellow stickies for room memories, and a green rectangle labelled `Notes` for building-wide notes.

1. **Get a Miro token** with the `boards:read` scope (Miro → Settings → Your apps, or a developer app) and put it in `.env` as `MIRO_TOKEN`. Optionally set `MIRO_BOARD_ID` (the part after `/board/` in the board URL).
2. **Check the board first** with a dry run. It creates nothing except `projects/<slug>/import_config.yaml` (colour settings, made on the first run) and the files in `import/` (in `import/attempt/` when the project already exists), and prints every fill and sticky colour it found, then the report:
   ```sh
   cd backend
   uv run python -m app.importers.miro --project old-school --dry-run
   ```
   If your door or window colours are listed as `room`, add their hex values to `projects/old-school/import_config.yaml` and run it again.
3. **Import:**
   ```sh
   uv run python -m app.importers.miro --project old-school --name "Old school"
   ```
   It prints a one-line summary and writes `projects/old-school/` with the scene, a first history entry "Imported", default materials and a flat roof.

| Option | Meaning |
|---|---|
| `--board <id>` | Board to read; defaults to `MIRO_BOARD_ID` |
| `--project <slug>` | Project folder name (lowercase words joined by `-`); required |
| `--name "..."` | Display name; defaults to the slug in title case |
| `--dry-run` | Print the colours found and the report; create no project |
| `--force` | Re-import an existing project. The new shell becomes a new history entry, so the old one can still be restored; objects, pins and materials start fresh |
| `--llm-notes` | Let Claude (`ANTHROPIC_MODEL`) read free-text level notes such as "two steps down"; the report shows how each note was read |
| `--from-json <path>` | Read a saved board dump (e.g. an earlier `import/miro_raw.json`) instead of calling Miro |

Every run saves the raw board as `projects/<slug>/import/miro_raw.json` and writes `import/import_report.md`: the scale used, every room (area, tags, level, ceiling), every opening with its wall, steps, building notes, warnings (snapped gaps, overlaps, openings that cross no wall, unmapped colours, ...), ignored board items and the colour table. Read it after each import. For a project that already exists, a dry run or a failed re-import writes these two files to `import/attempt/` instead, so `import/` keeps describing the current shell until a re-import succeeds. The importer exits with an error, and creates no project, when the board has no scale bar or more than one, no rooms, rooms that do not touch each other, or a courtyard (a hole in the footprint). It also refuses a project folder that holds a `scene.json` or `history/` but no `project.json`, and leaves that folder untouched.

What it does with imperfect drawings: gaps and overlaps between room edges up to 15 cm (at scale) are closed, and nearby edges that cannot all be lined up without moving one further than that are reported; larger overlaps are cut out of the bigger room; a door that just misses a wall attaches to a wall up to 30 cm away; a room whose tallest door does not fit under its ceiling gets a higher ceiling; a door between rooms on different levels without a `steps N` note gets steps of about 18 cm; an `h=` of 0 or less, or a negative `sill=`, is replaced by the default; when two `steps N` notes point at the same door, the one touching it wins. Each of these is listed in the report.

### A starter board to copy

To get a ready example (four rooms, a wing, a sunken gym, doors, windows, a passage, notes, plus a Legend frame that explains every shape and colour), create it in your own Miro account. The token needs the `boards:read` **and** `boards:write` scopes:

```sh
cd backend
uv run python scripts/make_starter_board.py
```

It always creates a new board called "RoomLoom starter" and prints its id and link. Duplicate it and redraw, or check it with `--dry-run` (`--board <id>`). Free-standing walls (a partition that touches no other wall) cannot be drawn yet; the Legend says so.

## View the building shell

With `make dev` running, open http://localhost:5173/?debug=shell. It loads `example-l-house` from the backend and shows its locked shell: floors, ceilings, walls with door and window holes, frames, glass and the gym's steps. Drag to orbit, scroll to zoom, right-drag to pan. The axes helper at the origin points east (red, +X), up (green, +Y) and south (blue, +Z). The box in the top-left corner shows the draw call count and what is under the mouse pointer (for example `wall_face · w_hall_room_1 · left · room r_room_1`).

URL parameters (all optional):

| Parameter | Example | Meaning |
|---|---|---|
| `project` | `project=my-school` | Show another project. |
| `cam` | `cam=10,1.6,13` | Camera position in world metres (x, y, z). |
| `look` | `look=7.8,0,10` | Point the camera looks at. |

Ceilings face down and walls face outwards, so from above you see into the rooms through the ceilings. Lighting is deliberately plain on this page; the real renderer comes later.

## Scene conventions

- Units are metres, and Y is up. A Miro plan point `(x, y)` maps to the world point `(x, 0, y)`. North is −Z, the top of the board.
- Polygons are stored counter-clockwise **as seen from above** (as drawn on the board), without repeating the first point. Wall sides "left" and "right" are as seen from above when walking from `a` to `b`.
- An opening's `sill` and `height` are measured from the higher floor of the two rooms beside its wall.
- A primitive's local origin is its bottom centre, and its front faces local −Z (north at yaw 0).
- Coordinates are rounded to millimetres. `scene.json` is written atomically, with a stable key order.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `Port 5173 is in use` or `address already in use` (8000) | Another dev server is still running. Find it with `lsof -nP -iTCP:5173 -sTCP:LISTEN` (or `:8000`) and stop it. |
| The badge stays `backend: down` | Check the `make dev` output for a backend error, and run `curl localhost:8000/api/health`. |
| `error: Miro refused access (401)` when importing | `MIRO_TOKEN` in `.env` is missing, expired or lacks the `boards:read` scope. |
| uv can't find Python 3.12 | Run `uv python install 3.12`. |
| `npm` complains about the Node version | Upgrade Node to 22.12 or newer. |
| Blank page with no cube | Open the browser console. The page needs WebGL, which every current desktop browser has. |
| `?debug=shell` shows `Loading scene of … failed: HTTP 404` | The project slug does not exist under `projects/`; check the `project` parameter. Any other error usually means the backend is not running. |
